# หลักการวิศวกรรมของ manual-kit

สรุปภาษาไทยของ 23 principles ของ pstack โดย Lauren Tan (poteto), MIT License, Copyright (c) 2026 Lauren Tan —
https://github.com/backnotprop/pstack (ไฟล์ `skills/principle-*/SKILL.md`) และใส่ตัวอย่างจาก repo นี้

การรีวิวอ้างเลขหลักการได้ (เช่น "ขัด #13") หลักการไหนถูกฝ่าซ้ำ ให้เปลี่ยนเป็นเทสต์หรือกฎตรวจตาม #23

## แกนหลัก

| # | หลักการ | ทำอย่างไร | ตัวอย่างใน manual-kit |
|---|---|---|---|
| 1 | ขี้เกียจอย่างมีวินัย | เลือกการแก้ที่เล็กที่สุดที่แก้ปัญหาได้ ไม่เผื่ออนาคต | adapter `generic` ใช้ regex ใน config แทนการเขียน adapter ใหม่ทุกเฟรมเวิร์ก |
| 2 | วางรากให้ถูก | เลือก type และโครงข้อมูลก่อนเขียน logic | `Adapter` มีสามเมธอด (`items`, `uiStrings`, `data`) ทุกคำสั่งใช้ร่วม |
| 3 | ออกแบบใหม่จากหลักการแรก | ความต้องการใหม่ = ออกแบบเหมือนมีตั้งแต่วันแรก ไม่ปะ | หน้าจอ terminal ใช้ highlight/steps/clip ชุดเดียวกับหน้าเว็บ ไม่ทำระบบภาพแยก |
| 4 | ตั้งคำถามกับสมมติฐาน | แก้แล้วล้มที่เดิมซ้ำ ≥ 2 ครั้ง ให้หยุดและถามว่าสมมติฐานผิดไหม | Word ค้างซ้ำ → เลิกใช้ Word อัตโนมัติเป็นค่าเริ่มต้น |
| 5 | ลบก่อนเพิ่ม | ลบโค้ดตายและของซ้ำก่อนสร้างของใหม่ | โฟลเดอร์ `skill/` และการติดตั้งด้วย `npm link` ถูกแทนด้วย plugin |
| 6 | ลดภาระคนอ่าน | ยุบชั้นที่ไม่จำเป็น ลดขอบเขต state ที่เปลี่ยนได้ | ไฟล์ที่ส่งไปกับเครื่องมือหาได้จากจุดเดียว (`src/paths.ts`) |
| 7 | มุ่งผลลัพธ์ปลายทาง | เดินไปสถาปัตยกรรมเป้าหมาย ไม่สร้างโค้ดชั่วคราวให้ช่วงกลางสวย | |
| 8 | ประสบการณ์มาก่อน | เลือกความสะดวกของผู้ใช้เหนือความสะดวกของผู้สร้าง | ติดตั้งสองคำสั่ง ไม่ต้องรัน npm เอง |
| 9 | สำรวจทางเลือกให้สุด | งานที่ไม่มีแบบอย่าง ทำต้นแบบ 2–3 แบบแล้วเทียบ | |
| 10 | สร้างคานงัด | สร้างเครื่องมือที่ทำงานหรือพิสูจน์งาน แทนการทำมือ | `check`, `snap`, `check --docx` |

## สถาปัตยกรรม

| # | หลักการ | ทำอย่างไร | ตัวอย่างใน manual-kit |
|---|---|---|---|
| 11 | จำลองโดเมนเป็นโครงสร้าง | ใส่โดเมนลงโครงสร้างแทน if กระจาย | หัวข้อ how-to ห้าส่วนอยู่ในรายการเดียว (`src/how-to.ts`) ใช้ทั้ง `new-page` และ `check` |
| 12 | วินัยที่ขอบระบบ | ตรวจข้อมูลภายนอกที่ขอบ ภายในเชื่อ type | config, shots.yaml, front matter ผ่าน zod ที่ `src/config.ts`, `src/shots.ts`, `src/pages.ts` |
| 13 | วินัยของระบบ type | ทำให้สถานะผิดเขียนไม่ได้ ครอบทุก variant | `AdapterConfig` เป็น discriminated union, `switch` ครบทุกชนิด |
| 14 | ทำซ้ำแล้วได้ผลเดิม | คำสั่งที่รันซ้ำต้องจบที่สถานะเดียวกัน | `publish outline` อัปเดตแทนสร้างซ้ำ (`outline.json`), `discover` ไม่มี timestamp |
| 15 | ย้ายผู้เรียกแล้วลบ API เก่า | ย้ายผู้เรียกและลบของเก่าในรอบเดียว | |
| 16 | แยกก่อนต่อคิว state ร่วม | ขจัดการแชร์ก่อนคิดเรื่องคิว | LibreOffice ใช้โฟลเดอร์ profile ของตัวเอง ไม่ชนกับตัวที่ผู้ใช้เปิดอยู่ |

## การตรวจสอบ

| # | หลักการ | ทำอย่างไร | ตัวอย่างใน manual-kit |
|---|---|---|---|
| 17 | พิสูจน์ว่าใช้ได้จริง | ตรวจกับของจริง ไม่ใช่ "compile ผ่าน" | อ่าน PDF ที่ build จริง, `snap` ที่ 1280/390, `check --docx` |
| 18 | แก้ที่ต้นเหตุ | ทำให้เกิดซ้ำก่อน ถามว่าทำไมจนถึงต้นเหตุ | escape ข้อความครั้งเดียวที่จุดเดียว แทนการถอด `&quot;` ทีหลัง |
| 19 | ลำดับหน่วยที่ตรวจได้ | แบ่งงานเป็นหน่วยเล็กที่ตรวจได้ commit ทีละเรื่อง | ประวัติ commit ทีละความสามารถ (CHANGELOG.md) |
| 20 | ทดสอบพฤติกรรม ไม่ใช่ไส้ใน | เรียกแบบที่ผู้ใช้เรียก ตรวจผลที่เขาเห็น | เทสต์รัน CLI จริงกับโครงการตัวอย่าง อ่านข้อความใน PDF และ XML ใน DOCX |

| # | หลักการ | ทำอย่างไร | ตัวอย่างใน manual-kit |
|---|---|---|---|
